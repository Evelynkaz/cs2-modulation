# Архитектура cs2-modulation

Статус: черновик этапа 0. Документ описывает целевой дизайн и то, чем мы
отличаемся от референса [`NC1107/cs2-smoke-solver`](https://github.com/NC1107/cs2-smoke-solver)
(далее «референс», C#, снимок `9c9ba1a` от 2026-09-11). Конспект форматов
файлов — в [`FORMATS.md`](FORMATS.md).

## 1. Задача

Обратная задача для гранат CS2: по цели на карте найти все броски
(позиция ног, pitch/yaw, тип броска, клик), после которых граната
детонирует/останавливается в цели, и для каждого выдать
`setpos x y z; setang pitch yaw 0`, траекторию, точку приземления и
оценку стабильности.

Для смока цель — точка/зона остановки плюс (опционально) набор линий
видимости, которые облако должно перекрыть. Для флешки и HE — точка
взрыва (в том числе в воздухе). Для молотова/зажигательной — точка
касания пола, на которой возникает огонь. Для декоя — точка остановки.

## 2. Поток данных

```
 CS2 install (только чтение файлов на диске)
   maps/<map>.vpk, pak01_dir.vpk, csgo_community_addons/<map>/*.vpk
        │  s2fmt: VPK → ресурс *_c → KV3 → PHYS / entities / world nodes / .nav
        ▼
   extract: политика CS2 (какие энтити твёрдые, стекло, статические пропы,
            атрибуты коллизий) → cache/<map>/<vpk-hash>/world.cgeo, nav.json,
            entities.json, standspots.bin, radar.png
        │
        ▼
   geom: TriMesh + BVH + воксели + фильтры по атрибутам
        │
        ▼
   sim: запуск броска → потиковый интегратор → детонация по типу гранаты
        │                                   → объём дыма, линии видимости
        ▼
   solver: standspots → грубый перебор по вокселям → уточнение
           → проверка по треугольникам с шевелением прицела → стабильность → ранжирование
        │
        ├── cli (clap): extract, info, throw, solve, standspots, calibrate, replay, serve, export-obj,
        │                smoke, sightline
        └── server (axum): REST + job id/прогресс + статика viewer/
                                   ▼
                              viewer/: 2D-радар, 3D-сцена (three.js), результаты
```

## 3. Крейты

Cargo workspace, `edition = "2024"`, общий `[workspace.dependencies]`.
Направление зависимостей строго сверху вниз, циклов нет:

```
s2fmt   (ни от кого)
geom    (ни от кого из наших; glam)
extract → s2fmt, geom
sim     → geom
solver  → sim, geom
calib   → sim, geom
server  → solver, sim, geom, extract
cli     → всё
```

### 3.1 `crates/s2fmt` — форматы Source 2

Чистый парсер без знаний о CS2-геймплее. Ошибки через `thiserror`,
каждый формат — отдельный модуль с юнит-тестами на синтетических
фикстурах, собранных нашим же кодом (writer-хелперы только в `#[cfg(test)]`).

- `vpk` — VPK v1/v2: дерево директории, чтение записей из `_dir.vpk`
  и `_NNN.vpk` (`memmap2`), preload-данные, проверка CRC32.
- `resource` — контейнер `*_c`: заголовок, таблица блоков, доступ к
  `DATA`/`PHYS`/`RERL`/`NTRO`… по 4CC.
- `kv3` — KV3 binary (все версии, что поддерживает VRF; LZ4 block и zstd)
  и KV3 text. Единое дерево `kv3::Value`.
- `phys` — `PhysAggregateData` → «сырые» части: hulls (полурёберная
  структура), meshes (треугольники + материалы), collision attributes
  (группа, interact-as/with/exclude строки), surface property hashes.
  Только чтение структуры, без триангуляции под нужды физики.
- `entities` — entity lump (KV3 и старый бинарный вариант с хэшированными
  ключами), классы/origin/angles/model/targetname.
- `worldnode` — `SceneObjects`/`AggregateSceneObjects` из `*.vwnod_c`
  (модель + матрица) для статических пропов.
- `nav` — CS2 `.nav`: области (полигоны), хуллы, связи, лестницы.

Зависимости: `thiserror`, `lz4_flex` (чистый Rust), `ruzstd`
(чистый Rust — не тянем C-toolchain в CI), `crc32fast`, `memmap2`.

### 3.2 `crates/extract` — политика извлечения карты (новый крейт)

**Отличие от предложенной структуры.** В исходном плане извлечение
физики лежало в `s2fmt`. Мы разделяем: `s2fmt` умеет *прочитать* PHYS,
а решение «что из этого твёрдое для гранаты» — это знание о CS2,
которое меняется с патчами и калибруется по игре (у референса оно
переписывалось десятки раз: `prop_dynamic`, стекло, retake-браши,
`startdisabled`-блокеры, community-addon VPK). Держать это отдельно —
значит сохранить `s2fmt` стабильным и тестируемым без игровых файлов, а
политику — в одном месте.

Задачи:
- триангуляция hull'ов из полурёбер, трансформация частей;
- мёрж: `world_physics.vmdl_c` + твёрдые brush-энтити
  (`func_brush`, `func_clip_vphysics`, двери, `func_breakable`) +
  статические пропы из world nodes + стеклянные `prop_dynamic`
  (классификация по `prop_data.base = Glass.Window`, фолбэк по пути модели);
- таблица атрибутов коллизий на треугольник (исходные группы + синтетические
  `EntitySolid`, `EntityDoor`, `EntityBreakable`, `EntityPhysicsClip`);
- кэш `cache/<map>/<vpk-sha256-16>/` + `manifest.json` (версия схемы,
  build id из `steam.inf`, хэши исходных VPK); битая карта даёт
  понятную ошибку и не мешает остальным (этап 8).

### 3.3 `crates/geom` — геометрия

- `TriMesh`: вершины `f32`, индексы, атрибут на треугольник (`u16`),
  таблица атрибутов со строками interact-as/exclude.
- `CollisionFilter`: битовая маска атрибутов, строится из правил:
  `grenade()` (как `GrenadeSolidFilter` референса: не блокируют
  `playerclip`/`npcclip`/`sky` в interact-as и всё, где exclude содержит
  `csgo_thrown_grenade`), `player()`, `vision()` и ручная маска
  `--attrs "Default,default,…"` для совместимости с CLI референса.
- `Bvh`: SAH, плоский массив узлов, построение по отфильтрованному
  подмножеству. Запросы: raycast (Möller–Trumbore, явные `t_min/t_max`
  у каждого вызывающего — урок F2 из аудита референса), sweep AABB
  против треугольников (SAT, 13 осей, нормаль контакта с учётом
  рёберных осей — референс проверил, что игра ведёт себя именно так),
  пересечение бокса, «первый пол под хуллом».
- `VoxelGrid`: битовая занятость, DDA, построение через tri-box SAT,
  параллельно (`rayon`).
- `export-obj`: OBJ с группами по атрибутам (проверка в Blender).
- Бенчмарки `criterion`: построение BVH, raycast, sweep, воксели.

Отличие: у референса — однородная сетка с CSR-бакетами. Мы реализовали оба
бэкенда за общим трейтом `Collider` и по результатам бенчмарка на реальной
карте (mirage) на этапе 3 решили так: `UniformGrid` — для точных gренад-
свипов хулла (совпадает с референсом бит-в-бит, включая разрешение ничьих
по `t`); `Bvh` — для линий видимости, прочих длинных лучей и box-запросов
(не наследует слепое пятно сетки на швах, см. ниже). Числа (mirage,
однопоточно): свип хулла гранаты — сетка ~6.7 млн/с против BVH ~2.0 млн/с;
`blocked` — BVH ~2.0 млн/с против сетки ~1.6 млн/с; `box_intersects` — BVH
~4.8 млн/с против сетки ~1.9 млн/с; воксельная сетка 16u строится за
~20–35 мс. `UniformGrid` также наследует слепое пятно референса: попадания
точно в угол/ребро вокселя её DDA-обход может пропустить (см. `bvh.rs` и
`collider.rs`) — для линий видимости это хуже, чем лишний ложный контакт,
поэтому они идут через `Bvh`.

### 3.4 `crates/sim` — симуляция гранат

Числа — `f32`, как в движке и в референсе (важно для совпадения
тиков и порогов). Все константы — в `ThrowConstants` со ссылкой на
источник в комментарии; значения по умолчанию в коде, переопределение
файлом `config/throw-constants.json` (имена полей совместимы с
`throw-constants.json` референса).

**Модель броска** (референс, `physics-sim.md`, измерено по телеметрии сервера):
- эффективный pitch: `pitch - (90 - |pitch|)/90 * 10`;
- точка выпуска: `eye + forward * 16`; глаза 64.06 стоя / 46.04 присев;
- скорость 675 × {1.00 левый, 0.65 оба, 0.30 правый};
- прыжок: +273.6 u/s по z (присед-прыжок +277.5), подъём точки выпуска
  26.1/20.0/14.0 для левого/обоих/правого;
- run-jump: +306 u/s вдоль направления движения (W, ±45°, ±90°);
- **walk, run (без прыжка)**: в референсе нет измеренных констант →
  `TODO: calibrate`, эксперимент на практис-сервере (см. §7).

**Движение игрока до выпуска гранаты** (`sim::player`, **нет у референса**).
Референс считает прыжок константой: +273.6 u/s и подъём точки выпуска —
это верно только на ровном открытом полу. Есть лайнапы, где геометрия
сама двигает игрока во время прыжка или разбега: прыжок с наклонной
поверхности («горки»), упор хулла в угол или выступ, который сдвигает
модельку, удар головой о низкий потолок, соскальзывание с края ящика.
Такие броски должны поддерживаться. Для этого `sim::player` моделирует
хулл игрока 32×32×72 (54 присев) потиково: гравитация, импульс прыжка,
collide-and-slide по плоскостям контакта (как `TryPlayerMove` в Source),
ступеньки, стояние на наклоне ≤ `sv_standable_normal`. Точка выпуска и
скорость гранаты берутся из **фактического** состояния игрока в тике
выпуска: позиция глаз + смещение, скорость игрока × множитель.

Требование совместимости: на ровном полу `sim::player` обязан
воспроизводить измеренные референсом значения (273.6 / 277.5 u/s,
подъём 26.1 / 20.0 / 14.0u, run-jump 306 u/s) — это регрессионный тест.
Параметры, которых нет в референсе (импульс прыжка, тик выпуска по
кликам, трение, ускорение, максимальная скорость с гранатой,
поведение на наклонах и у углов), — `TODO: calibrate` в конфиге и
отдельный протокол экспериментов на практис-сервере (этап 4/7).
Солвер помечает лайнап флагом `movement_constrained`, если траектория
игрока отличается от «ровной» модели больше чем на порог, и даёт
такому броску отдельную оценку стабильности по сдвигу ног.

**Интегратор** (референс, `SimulateExactRaw`): тик 1/64 с, 2 физических
подшага; клемп `sv_maxvelocity` 3500 по осям; гравитация 800×0.40;
трапеция по z; sweep бокса ±2u; отражение + STOP_EPSILON 0.1 +
упругость 0.45; демпфирование пола (n.z>0.7, скорость по полному тику
> 690, угол круче 60°): ×(1.5−|cos|); остановка при скорости после
отскока < 19.685 на полу; до 2 контактов за подшаг; стекло — проход
с ×0.40 и «разбитой» панелью до конца полёта; без качения, без
трения, без edge-tipping (всё это референс опроверг на корпусе).

**Детонация** — трейт `GrenadeKind`:
| Граната | Условие | Источник значений |
|---|---|---|
| smoke | остановка | референс (измерено) |
| decoy | остановка | TODO: подтвердить, что физика полёта та же |
| flashbang | таймер | TODO: проверить по файлам игры/практис-серверу |
| HE | таймер | TODO: то же |
| molotov / incendiary | касание достаточно горизонтальной поверхности или таймер; в воздухе — без огня | TODO: порог наклона и таймер из convar'ов (`help` на практис-сервере) |

Ни одно из значений для flash/HE/molotov/decoy не берётся «из памяти»:
на этапе 7 сначала ищем их в файлах игры (`scripts`, `weapons` vdata в
`pak01_dir.vpk`), затем подтверждаем экспериментом.

**Дым и видимость** (референс, эвристика, не калибровалась по игре):
приоритетный flood-fill по вокселям 16u от точки остановки, радиус 144u
(CS:GO 288u диаметр), бюджет клеток = объём полушара в открытом
пространстве, растяжение до ×1.75 в замкнутых объёмах, «тяга вниз» 0.8;
консервативный режим 100u. Перекрытие линии видимости: DDA по вокселям
считает клетки дыма, чистота линии от геометрии — по точным треугольникам.

### 3.5 `crates/solver` — обратная задача

1. **Standspots** (референс `StandSpots.cs`): решётка 16u, опорные высоты
   сдвигом бокса 32×32, хулл 72/54 (стоя/присед), связность flood-fill от
   nav-областей: шаг 18u, прыжок 57u, присед-прыжок 66u (TODO: calibrate),
   спуск до 210u, не дальше 6 шагов от nav. Предрасчёт один раз на карту.
2. **Отбор origin'ов** по радиусу досягаемости (таблица дальности по типу
   и клику, измеряемая симулятором на плоскости, как `ReachTable`).
3. **Грубый перебор** по вокселям: сетка yaw/pitch 2°, pitch до −65°
   (−89° для близких целей), все клики и направления бега.
4. **Уточнение**: лучшие near-miss'ы на решётке в 1/4 шага.
5. **Точная проверка** по треугольникам: переприцеливание к цели в окне
   ±2 шага по 0.6°, приёмка по точной дистанции до цели.
6. **Стабильность**: доля попаданий при шевелении прицела (5 точек ±0.6°)
   плюс разброс остановки при сдвиге ног на 0.25u. Референс показал, что
   одна «доля попаданий» слабо предсказывает реальную ошибку (r = −0.117),
   поэтому отдаём обе величины раздельно и оценку ошибки человека.
   Для jump / crouch-jump / run-jump добавляется шевеление **тайминга**:
   выпуск на ±1–2 тика относительно прыжка (через `sim::player`), для
   run-jump — ещё и скорость разбега; лайнап, который работает только при
   идеальном тайминге, так и помечается.
7. **Ранжирование** с детерминированным тай-брейком (origin → угол →
   клик), чтобы два прогона давали одинаковый порядок (урок референса).

Параллелизм — `rayon`; отмена через `AtomicBool`, прогресс через колбэк.

### 3.6 `crates/calib` — калибровка

- Формат `data/throws.json` совместим с референсом
  (`throw`/`landing` — строки `getpos`, `type`, `strength`, `measure`).
- Подбор констант покоординатным спуском (как у референса) с явным
  списком «инженерных» констант, которые **не** подбираются по точкам
  остановки (gravity, elasticity и т.д. — у референса такой фит однажды
  дал ложную гравитацию 0.34).
- `replay`: прогон корпуса валидации референса
  (`refs/cs2-smoke-solver/data/validation/*.json`, ~10 тыс. реальных
  бросков с `Pos/Vel/Feet/Yaw/Pitch/RealRest`) против нашей геометрии —
  главный офлайн-бенчмарк точности без игры. Корпус лежит вне репозитория
  и в git не попадает. Оговорка: он записан на клиентских билдах
  2000839–2000899 (сервер — до 2000908; поле `build` есть в каждом отчёте).
  Сравниваем только отчёты, чей билд совпадает с билдом извлечённых VPK;
  если VPK карты изменился, расхождение означает смену карты, а не баг.

### 3.7 `crates/server` — `axum` + `tokio`

- `GET /api/maps`, `GET /api/maps/{map}` (границы, радар, callouts, спавны);
- `GET /api/maps/{map}/mesh?filter=grenade` — бинарный меш для three.js;
- `POST /api/jobs` (solve) → `{id}`; `GET /api/jobs/{id}` — прогресс и
  результат; `DELETE /api/jobs/{id}` — отмена;
- `GET /api/trajectory?...` — симуляция одного броска;
- статика `viewer/`.

Тяжёлые вычисления — в `spawn_blocking` / отдельном пуле `rayon`;
ограничение числа одновременных задач. Кэш результатов на диске с
ключом из содержимого: хэш геометрии + хэш констант + версия солвера
(у референса ручной `QueryVersion` забывали увеличивать — не повторяем).

### 3.8 `crates/cli` — `clap`

`extract`, `info`, `export-obj`, `throw` (alias `simulate`), `smoke`,
`sightline`, `standspots`, `solve`, `calibrate`, `replay`, `serve`.
Бинарник `cs2mod`.

### 3.9 `viewer/`

Без сборщика: нативные ES-модули, `three.js` (и `OrbitControls`)
вендорятся в `viewer/vendor/` с лицензией. Модули: `api.js`, `radar.js`
(2D, canvas), `scene3d.js`, `results.js`, `state.js`. Радарная картинка
берётся из файлов игры на этапе extract и лежит в `cache/`, не в git.

## 4. Данные и кэш

| Путь | Что | В git |
|---|---|---|
| `config/` | конфиги, переопределения констант | да |
| `crates/*/tests/fixtures/` | маленькие синтетические фикстуры, созданные нами | да |
| `data/` | `throws.json`, пользовательские замеры, выгрузки | нет |
| `cache/` | извлечённая геометрия, standspots, радары, кэш решений | нет |

Путь к установке CS2 задаётся `--game` или `CS2_GAME_DIR`, в репозиторий
не пишется.

## 5. Жёсткие ограничения

- Никаких файлов игры в git (`data/`, `cache/` в `.gitignore`).
- Никакого взаимодействия с процессом игры. **Отличие от референса:**
  у него калибровка и валидация шли через плагин CounterStrikeSharp на
  сервере (хуки памяти, программные броски, потиковая телеметрия).
  Мы этого не делаем. Наши источники истины: (1) константы и выводы
  референса, (2) его опубликованный корпус валидации (офлайн `replay`),
  (3) ручные замеры пользователя `getpos` на практис-сервере.
- Константы — только со ссылкой на источник или `TODO: calibrate`.

| Язык | C#/.NET 10, VRF как библиотека | Rust, свой парсер по VRF |
| Гранаты | только smoke | smoke, flash, HE, molotov/incendiary, decoy |
| Типы броска | stand, crouch, jump, crouch-jump, run-jump | + walk, run (после калибровки) |
| Движение игрока | константы прыжка/бега (только ровный пол) | потиковый хулл игрока: наклоны, углы, потолки |
| Калибровка | плагин на сервере, телеметрия | ручные getpos + replay чужого корпуса |
| Коллизии | однородная сетка CSR | BVH (+ сравнение бенчмарком) |
| Nav | через VRF | свой парсер по VRF |
| Промежуточный формат | `.s2geo` | `.cgeo` + manifest с хэшами VPK |
| Долгие запросы | NDJSON-стрим | job id + прогресс + отмена |
| Инвалидация кэша | ручной `QueryVersion` | хэш содержимого |
| Порядок результатов | исправлен поздно | детерминированный с первого дня |

## 7. Известные подводные камни (из документов референса)

- `prop_static`: хуллы — в собственных `.vmdl_c`, не в world_physics;
  `AggregateSceneObjects` часто без коллизии вовсе.
- `prop_dynamic` почти всегда **не** блокирует гранату (кроме стекла);
  мёрж всех `prop_dynamic` стоил сотни промахов на nuke/mirage.
- `passbullets` блокирует гранату, если exclude не содержит
  `csgo_thrown_grenade`; `csgo_grenadeclip` блокирует.
- `func_brush`/`func_clip_vphysics` со `startdisabled=1` и retake-браши
  не должны попадать в меш.
- Community-карты держат модели в `csgo_community_addons/<map>/`.
- Nav-высота — среднее углов полигона, до 5u ниже пола; ноги ставить по
  опоре всего хулла 32×32, не по лучу из центра; `setpos` + 0.03u зазор.
- Точка спавна-энтити висит в воздухе — опускать на пол.
- Отрицательные результаты референса («не повторять»): сфера вместо бокса,
  уменьшенный хулл, edge-tipping, отдых только на гранях, порог наклона
  для отдыха, roll-out, модель «конец тика» для контакта.
- CS2 обновляет карты: корпус, записанный на старом билде, врёт.
- Детерминизм: тай-брейки по параметрам броска, а не по порядку потоков.

## 8. Открытые вопросы (эксперименты пользователя)

1. `getpos` в CS2 — глаза или ноги? Референс трактует выход `getpos`
   как позицию глаз, а `setpos` — как ноги. Проверить: `getpos` стоя,
   затем вставить вывод и снова `getpos`.
2. Walk/run броски: скорость игрока при ходьбе/беге с гранатой в руке и
   множитель, с которым она добавляется к скорости гранаты.
3. Таймеры и пороги flash/HE/molotov/decoy.
4. Высота присед-прыжка (66u в референсе помечено как TODO).
5. Движение игрока при прыжке у наклонов/углов/низких потолков: серии
   одинаковых бросков с `setpos` у такой геометрии и `getpos` места
   приземления гранаты — эталон для `sim::player`.
6. Jump throw: в CS2 на официальных серверах мульти-бинды запрещены
   (`cl_allow_multi_input_binds 0`, август 2024), прыжок и отпускание
   кнопки делаются вручную; референс измерил выпуск «через несколько тиков
   после прыжка» (+273.6 u/s). Нужно измерить разброс по задержке
   отпускания (0…N тиков) и сравнить с бросками через бинд на практис-сервере,
   чтобы солвер давал для jump throw честную стабильность по таймингу и
   инструкцию «как бросать».
7. Sub-tick ввода: референс моделирует только 2 физических подшага на
   контакте; влияние момента нажатия внутри тика на выпуск не изучено.
